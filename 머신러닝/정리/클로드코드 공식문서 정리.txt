2.클로드코드의 작동방식
*1.클로드코드의 작동방식
  에이전트는 컨텍스트수집,작업수행,결과검증의 루프를 거치면서 진행함	
  물론 무조건 이걸 거치는게 아니라,만약 코드베이스를 이해하라고만 하면 수집만 하는 이런식임
  사용자도 여기서 언제든지 중단할수있고,추가컨텍스트를 제공할수있고,다른접근방식을 시도하게 요청할수있음
  
  클로드의 내장 툴은
    파일작업:파일읽기,코드편집,새파일생성,이름변경 및 재구성
	검색:패턴으로 파일찾기,정규식으로 내용검색,코드베이스 탐색
	실행:셸명령 실행,서버시작,테스트실행,git사용
	웹:웹 검색,문서 가져오기,오류 메시지 조회
	코드인텔리전스(플러그인필요):편집후 타입오류 및 경고확인,정의로이동,참조찾기
  가 기본적으로 있음
  
  만약 '실패한 테스트를 수정해'라고 한다면
	테스트 스위트를 실행하여 무엇이 실패하는지 확인
	오류 출력 읽기
	관련 소스 파일 검색
	해당 파일을 읽어 코드 이해
	파일을 편집하여 문제 수정
	테스트를 다시 실행하여 검증	
  같은 순서대로 작업하게됨
  
  클로드코드가 기본적으로 접근할수있는곳은
    프로젝트의 하위디렉토리 및 파일,허가를 받은 다른곳의 파일
	터미널
	git상태
	claude.md
	오토 메모리(MEMORY.md)
	설치한 플러그인 및 스킬
  에 접근할수있음
  
  클로드에선 모든 작업을 세션으로 분류하게됨
  세션은 현재 세션에서 변경한 파일 목록을 가지고있기때문에 필요하다면 되돌릴수있고,
  현재 세션을 분기따서 진행하는것도 가능함(claude --continue --fork-session)
	
*2.컨텍스트 윈도우
  컨텍스트 윈도우에는	
    대화 기록
    파일 콘텐츠 
    명령 출력 
    CLAUDE.md
    자동 메모리
    로드된 skills
    시스템 지침
  이 들어감
  컨텍스트의 크기가 한계에 도달하면 자동으로 컴팩트하지만,일반적으로는 컴팩트를 하지않게 세션메모리를 관리하는게 좋음
  또한 서브에이전트는 결과를 제외한 중간과정 컨텍스트를 메인에이전트에 추가하지않고,스킬은 설명을 제외한 내용은 요청을 해야 들어오게됨
	
*3.체크포인트
  클로드가 한 모든 파일편집은 되돌릴수있음
  문제가 발생하면 esc를 두번 눌러 이전상태로 돌리거나,클로드한테 요청할수있음
  체크포인트는 세션의 로컬에 저장되고,git과는 분리되어있고 이건 파일 변경만을 다룸
  원격작업(db,api,배포)등은 당연히 롤백할수없음
	
*4.클로드코드 팁

	체크아웃 흐름이 만료된 카드를 가진 사용자에게 손상되었습니다.

3.클로드코드 확장하기	
*1.개요
  클로드코드는 다양한 부분으로 확장할수있음
	CLAUDE.md는 Claude가 모든 세션에서 보는 지속적인 컨텍스트를 추가합니다.
	Skills는 재사용 가능한 지식과 호출 가능한 워크플로우를 추가합니다.
	MCP는 Claude를 외부 서비스 및 도구에 연결합니다.
	Subagents는 격리된 컨텍스트에서 자신의 루프를 실행하고 요약을 반환합니다.
	Agent teams는 공유 작업 및 피어 투 피어 메시징으로 여러 독립적인 세션을 조정합니다.
	Hooks는 결정론적 스크립트로 루프 외부에서  실행됩니다.
	Plugins 및 marketplaces는 이러한 기능을 패키징하고 배포합니다.	
  가장 잘 사용되는건 claude.md와 Skill임
  
*2.기능을 목표에 맞추기  
  스킬은 지식,워크플로우,지침을 포함하는 마크다운파일로 가장 유연한 확장임
  /스킬명 으로 명시적 호출을 할수도있고,클로드가 알아서 호출할수도있음
  스킬은 현재 세션에서 실행되거나,서브에이전트로 실행시킬수도있음
  
  클로드.md는 모든 대화에서 지속적으로 로드되는 컨텍스트로,프로젝트규칙이나 항상 수행해야하는 규칙을 넣기 좋음
  스킬은 클로드가 사용할수있는 지침,지식,워크플로우 컨텍스트로,재사용가능한 컨텐츠나,참조문서,반복가능한 작업을 넣기좋음
  서브에이전트는 요약된 결과를 반환하는 격리된 실행 컨텍스트로,컨텍스트격리,병렬작업,특화워커에 사용됨
  에이전트팀은 여러 독립적인 에이전트들의 세션을 조정하는방식으로,병렬연구,새 기능 개발,경쟁가설로의 디버깅등에 사용됨
  mcp는 외부서비스 연결에 사용되고,외부데이터또는 작업을 할때 사용됨,db쿼리,슬랙에 개시,브라우저제어등에 사용됨
  hook은 이벤트에서 실행되는 결정론적 스크립트로,예측가능한 자동화에 사용됨,이건 반드시 이벤트가 터지면 호출됨
  플러그인은 이런것들을 묶어서 패키징해둔것
  
*3.유사한 기능 비교	
  스킬과 서브에이전트의 차이점은,스킬은 재사용가능한 컨텐츠고 서브에이전트는 주세션과는 별개의 세션이라는것
  스킬은 참조(정보)일수도,작업(워크플로우)일수도 있음
  컨텍스트가 가득차는 작업일땐 서브에이전트를 사용하면되고,
  스킬과 서브에이전트를 같이 사용할수도있음
  스킬에서 서브에이전트를 통해 격리된 컨텍스트에서 실행하게할수도있고(context: fork)
  서브에이전트에서 스킬을 미리 로드할수도 있음(skills:필드)
  
  스킬과 클로드md의 차이점은 둘다 컨텍스트지만,
  클로드md는 모든세션에 자동으로 붙는 고정형 컨텍스트고,
  스킬은 필요해지면 추가되는 형태의 컨텍스트임
  또한 스킬은 워크플로우 트리거가 가능하고,클로드md는 고정형이라 안됨
  클로드md는 항상 수행해야 하는것을 넣으면되고,스킬은 가끔 필요한 참조자료나 호출가능한 워크플로우를 넣기좋음
  또한 클로드md는 200줄 이하로 유지하는게 좋고,넘어간다면 그걸 스킬로 이동시키거나 .clude/rules/파일로 분할하는게 좋음
  여기서 .clude/rules/은 파일 경로로 범위를 지정해서,해당하는 파일을 작업할때만 컨텍스트에 추가됨
  이건 언어별 또는 디렉토리별 가이드라인으로 주로 사용됨
  
  서브에이전트와 에이전트팀의 차이점은,서브에이전트의 결과는 호출자에게 반환되지만,에이전트팀에서는 완전히 독립적임
  통신도 서브에이전트는 주에이전트에게만 결과를 보고하지만,에이전트팀은 자기들끼리 서로 직접 메시지를 함
  즉 진짜 팀처럼 행동하고,그래서 토큰비용도 높음
  서브에이전트의 다음버전이 에이전트팀이라고 볼수있음
  
  mcp와 스킬의 차이점은,mcp는 클로드를 외부서비스와 연결하고,스킬은 클로드가 알아야하는 내용을 확장하면서 거기에 필요한 정보를 포함함
  즉 mcp는 외부와의 접근 도구고,스킬은 이런 mcp를 잘 사용하는 방법을 담고있음

*4.기능이 어떻게 계층화되는지 이해하기
  기능은 여러수준으로 정의될수있음,프로젝트레벨이나 사용자레벨,플러그인레벨등
  또한 클로드md파일을 하위디렉토리에 중첩하거나,모노레포의 특정패키지에 스킬을 배치할수도있음
  
  같은 기능이 여러 레벨에 존재할때의 계층화방식은
    클로드md:추가됨,모든수준이 동시에 클로드컨텍스트에 컨텐츠를 추가함
	  최상단의 파일은 시작시 로드되고,하위디렉토리는 작업할떄 로드됨
	  지침이 충돌한다면 알아서 조정하고,더 구체적인걸 일반적으로 우선함
	스킬,서브에이전트:이름으로 덮어씌워짐,같은이름이 여러레벨로 존재할때,우선순위에 따라 하나의 정의가 승리함,
	  보통 관리>사용자>프로젝트 순으로 이기고,
	  플러그인의 스킬은 네임스페이스를 붙여서 따로 관리하게됨
	MCP:이름으로 덮어씌워짐
	Hooks병합됨,모든 hook은 이벤트가 터지면 전부 실행됨
	
*5.기능 결합하기	
  각 기능들은 자신만의 문제를 해결함
  클로드md는 항상 필요로하는 컨텍스트를,
  스킬은 가끔 필요해지는 지식과 워크플로우를,
  mcp는 외부연결을,
  서브에이전트는 격리를,
  훅은 자동화를 처리함
  
  이런것들은 워크플로우를 따라 결합됨
  클로드md로 프로젝트 규칙을 정의하고,스킬을 배포 워크플로우에 사용하고,mcp를 db와 연결하고,hook을 편집후 린팅을 실행하는데 사용하는식
  
  대표적인 패턴으로
    스킬+mcp:mcp는 연결을,스킬을 사용법을 알려줌
	스킬+서브에이전트:스킬은 병렬작업을 위해 서브에이전트를 생성함
	클로드md+스킬:클로드md에 목차처럼 규칙을 넣어두고,그게 필요해졌을떄 스킬로 불러올수있음
	  예를들면 CLAUDE.md는 API 규칙을 따르세요(목차)라고 말하고, skill은 전체 API 스타일 가이드(상세내용)를 포함
	hook+mcp:훅은 mcp를 통해 외부작업을 트리거
  등이 있음

*6.컨텍스트 비용 이해하기
  추가하는 모든 기능(훅을 제외)은 클로드의 컨텍스트를 소비함
  그래서 꼭 필요한것만 적절한 위치에 넣는게 좋음
      기능	     로드 시기	      로드되는 내용	                 컨텍스트 비용
      CLAUDE.md	 세션 시작	      전체 콘텐츠	                 모든 요청
      Skill	     세션 시작+사용시	  시작 시 설명, 사용 시 전체 콘텐츠	 낮음(스킬의 개요만 추가됨)
      MCP 서버	 세션 시작	      모든 도구 정의 및 스키마	         모든 요청
      Subagent	 생성 시	      지정된 skill이 있는 새 컨텍스트	 주 세션에서 격리됨
      Hooks	     트리거 시	      없음(외부에서 실행)	             0, hook이 추가 컨텍스트를 반환하지 않는 한
	
*7.기능이 어떻게 로드되는지 이해하기	
  각 기능들은 세션의 다양한 지점에서 로드됨
  
  클로드md
    로드시기:세션 시작시 로드
	로드내용:모든 클로드md의 파일의 전체 내용
	상속:클로드는 루트부터 작업디렉토리까지의 모든 클로드md파일을 읽고 해당파일에 접근할때 하위디렉토리에서 중첩파일을 검색함
	비고:가급적 200줄이하로 유지,넘기면 스킬로 뽑기
  스킬
    로드시기:설명은 세션시작시 로드,컨텐츠는 사용시 로드
	로드내용:설명은 세션시작시 로드,컨텐츠는 사용시 로드
	선택방식:작업을 스킬설명과 비교해서 관련성이 있는지를 결정하고,/스킬명 으로 명시적으로 시킬수있음
	컨텍스트비용:사용하기전까진 낮음
	서브에이전트에서:서브에이전트에서의 스킬은 시작시 컨텍스트에 완전히 로드되고,이때 서브에이전트는 주세션에서 스킬을 상속받지못해서 명시적으로 지정해야함
	비고:disable-model-invocation: true을 사용하면 클로드가 스킬을 사용하지못하고,명시적으로 트리거를 해야만 하게 할수있음,
	  이건 사이드이팩트가 있는 작업에 유효
  MCP
    로드시기:세션시작시 로드
	로드내용:연결된 서버의 모든 툴 정의 및 json 스키마
	컨텍스트 비용:툴서치는 기본값으로 mcp도구를 컨텍스트의 최대 10%까지 로드하고,나머지는 필요할때까지 연기
	비고:MCP는 세션중간에 조용히 실패할수있으니 주의,이때는 서버가 연결해제되면 도구가 경고없이 사라짐
  서브에이전트
    로드시기:작업을 위해 사용자나 클로드가 생성
	로드내용:시스템프롬프트(보통 부모와 공유),에이전트의 스킬,클로드md(부모로부터 상속),git상태(부모로부터 상속),메인에이전트가 프롬프트로 전달하는 컨텍스트
	컨텍스트비용:주세션과는 격리되어서 결과를 제외하면 따로 메인 에이전트에 컨텍스트를 추가하진않음
	비고:결과만 필요한 작업에 사용하면 컨텍스트를 제한하고 결과만 받아쓸수있음 
  Hooks
    로드시기:트리거시
	로드내용:없음
	컨텍스트비용:0,hook이 추가 컨텍스트를 반환하지 않는 한
	비고:클로드의 컨텍스트에 영향을 주지않아야하는 사이드이펙트(예를들어 린팅이나 로깅등)에 이상적
	
	
4.클로드 디렉토리
  클로드코드는 Claude.md와 /.claude 디렉토리 안의 내용들을 주로 읽게됨
  이 안의 파일들은 선택사항이지만,유용함
  여기는 프로젝트레벨과 글로벌레벨로 나뉨
  
  
*1.프로젝트 레벨
  ** 이 아래는 프로젝트레벨의 프로젝트 루트에 속한 파일들
  
  Claude.md는 매 세션마다 들어가는 프로젝트 지침이고,공통규칙,공통명령,아키텍처등을 기록하기 좋고,200줄내외가 이상적
  빌드,테스트,포맷등 자주 사용하는 명령어를 목록으로 정리해두면 클로드가 매번 명령어를 입력하지않아도 바로 알수있음
  또한 루트 디렉토리에 넣기싫으면, .claude디렉토리 안에 넣어도됨
  
  .mcp.json은 mcp서버를 구성하는 json파일임
	{
	  "mcpServers": {
		"github": {
		  "command": "npx",
		  "args": ["-y", "@modelcontextprotocol/server-github"],
		  "env": {
			"GITHUB_TOKEN": "${GITHUB_TOKEN}"
		  }
		}
	  }
	}
  이런식으로 구성됨	
  이건 프로젝트 루트에 위치하고,.claude 내부에 있지않음
	
  .worktreeinclude는 git에서 무시된 파일을 새 워크트리에 추가할때 사용됨
	# Local environment
	.env
	.env.local

	# API credentials
	config/secrets.json
  이런식으로 gitignore처럼 적으면됨
  이건 보통 env파일같은걸 git에서 무시했을때, 새워크트리를 만들때 옮겨서 사용하기위해서 사용됨
  이건 프로젝트 루트에 위치하고,.claude 내부에 있지않음
  
  ** 이 아래는 .claude/안에 속한 디렉토리와 파일들
  
  setting.json은 클로드코드가 직접 적용하는 설정임
  여기엔
    권한:클로드가 특정 도구나 명령을 사용하기전에 허용,거부,요청을 미리 설정할수있음
	훅:특정 이벤트 발생시 지정된 스크립트 실행
	스테이터스라인:클로드가 작업할때 하단에 표시되는줄을 커스텀
	모델:이 프로젝트에서 사용할 기본 모델 선택
	env:세션마다 설정되는 환경변수
	아웃풋스타일:출력스타일 선택
  가 있고,와일드카드를 지원함(권한설정시 유용)
  예시는
	{
	  "permissions": {
		"allow": [
		  "Bash(npm test *)",
		  "Bash(npm run *)"
		],
		"deny": [
		  "Bash(rm -rf *)"
		]
	  },
	  "hooks": {
		"PostToolUse": [{
		  "matcher": "Edit|Write",
		  "hooks": [{
			"type": "command",
			"command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
		  }]
		}]
	  }
	}
  이런식으로 사용함
  
  settings.local.json은 settings.json을 재정의하는 로컬 설정임
  유저레벨로 settings.json이 있을때,이걸쓰면 그걸 건드리지않고 특정 프로젝트에서만 그 내용을 수정할수있음
  겹치는거만 덮어씌워지는식이라,기본적으로 settings.json+로 적용된다고 보면됨
  
  rules/디렉토리는 파일경로로 접근제어를 할수있는 규칙들을 넣어두는곳임
  즉 특정 경로의 파일을 작업할때만 컨텍스트에 추가되는 규칙을 추가할수있음
  이건 파일의 paths로 경로를 정하고,그밑에 프롬프트를 추가하는식으로 구성됨
  예시로 testing.md는
	---
	paths:
	  - "**/*.test.ts"
	  - "**/*.test.tsx"
	---

	# Testing Rules

	- Use descriptive test names: "should [expected] when [condition]"
	- Mock external dependencies, not internal modules
	- Clean up side effects in afterEach
  이런식으로 paths로 경로를 잡고,밑에 프롬프트를 추가하는식
  예시를 하나 더보면,이건 api디자인용으로 api-design.md임
	---
	paths:
	  - "src/api/**/*.ts"
	---

	# API Design Rules

	- All endpoints must validate input with Zod schemas
	- Return shape: { data: T } | { error: string }
	- Rate limit all public endpoints
  이런식으로 프로젝트의 구조가 정해져있을때 특정 디렉토리에 맞는 상태로 구성할수있음
  그래서 클로드.md에서는 프로젝트의 아키텍처를 정하고,그 하위 세부규칙을 rules로 빼는식의 패턴이 자주 사용됨
  
  skills/디렉토리는 스킬들을 모아두는 디렉토리임
  이 하위에 있는 디렉토리 하나하나 당 각각 하나의 스킬임
  기본적으로는 사용자와 클로드 모두 스킬을 사용할수있고,클로드는 사용하지못하게 할수도있음
  스킬은 인수를 허용하고,클로드는 스킬 디렉토리 경로를 알고있으니 그냥 언급만 해도됨
  그러니 그냥 언급만 하고,참조문서를 디렉토리에 같이 넣어서 스킬로 만들면됨
  또한 스킬의 이름은 해당 디렉토리의 이름임
  
  skill.md는 description에 적힌 요약설명과,disable-model-invocation으로 모델이 접근하게할건지 말건지(기본값 허용),실제 내용으로 구성됨
  예시로는
	---
	description: Reviews code changes for security vulnerabilities, authentication gaps, and injection risks
	disable-model-invocation: true
	argument-hint: <branch-or-path>
	---

	## Diff to review

	!`git diff $ARGUMENTS`

	Audit the changes above for:

	1. Injection vulnerabilities (SQL, XSS, command)
	2. Authentication and authorization gaps
	3. Hardcoded secrets or credentials

	Use checklist.md in this skill directory for the full review checklist.

	Report findings with severity ratings and remediation steps.
  이런식으로 구성됨
  여기서 checklist.md처럼 외부로 파일을 빼고싶은경우,스킬디렉토리에 넣어두면 알아서 읽음
  이때 참조문서,템플릿,스크립트등 모든 파일을 읽을수있음
  bash인젝션때 스크립트를 쓰려면 ${CLAUDE_SKILL_DIR}을 써야한다는거만 알면됨
  
  commands/는 예전에 쓰던거임,요즘은 스킬로 통합돼서 안씀
  
  output-styles/은 출력스타일 설정임,보통은 글로벌로 쓰지만 여기서도 쓸수있음
  
  agents/디렉토리는 하위에이전트를 정의하는곳
  특정 하위 에이전트를 반복 사용할때,여기서 정의하고 불러다가 쉽게 만들수있음
  이 하위의 마크다운파일마다 하나의 에이전트타입이라고 보면됨
  이것도 스킬이랑 비슷한느낌으로 만들어지게됨
  예시로 코드리뷰를 하는 code-reviewer.md는
	---
	name: code-reviewer
	description: Reviews code for correctness, security, and maintainability
	tools: Read, Grep, Glob
	---

	You are a senior code reviewer. Review for:

	1. Correctness: logic errors, edge cases, null handling
	2. Security: injection, auth bypass, data exposure
	3. Maintainability: naming, complexity, duplication

	Every finding must include a concrete fix.
  이런식으로 작성됨
  기본적으로는 description만 보여지고,이걸 선택하면 이안에 적힌 내용을 사용해서 하위 에이전트를 생성하는,스킬과 비슷한 매커니즘임
  여기서의 description는,클로드에게 언제 작업을 위임해야하는지를 알려주고,tools에선 허용되는 도구목록을 표시하고,본문은 시스템프롬프트임
  
  agent-memory/는 서브에이전트의 메모리임
  메인세션의 오토메모리처럼 서브에이전트 각각의 자체 메모리파일 위치임
  이건 agent-memory/에이전트이름/memory.md 로 구성됨
  오토메모리니까 신경쓰지않아도됨,서브에이전트가 직접 생성하고 업데이트함
  
*2.글로벌레벨
  글로벌레벨은 프로젝트에 속하지않아서 커밋되지않는다는 특징을 주로 이용함(로컬에만 존재하게됨)
  .claude.json은 settings.json에 포함되지않는 상태정보를 포함함
  이건 테마,Oauth 세션,프로젝트별 신뢰설정,개인mcp서버,ui토글등을 저장하게됨
  보통 직접편집하기보단,다른경로를 통해 관리됨
  
  .claude/는 프로젝트의 .claude/와 거의똑같음,대신 작업하는 모든 프로젝트에 적용되고,어디에도 커밋되지않는다는 차이가 있음
  이하의 모든것들은 ,claude/안에 들어있음
  
  claude.md는 전역 claude.md고,이건 프로젝트의 claude.md와 함께 로드되므로 둘다 컨텍스트에 포함됨
  지침이 충돌하면 프로젝트 레벨을 우선시하게 프롬프팅되어있음
  보통 응답스타일,커밋형식,개인적인규칙등 모든곳에 적용되는 기본설정을 여기에 저장함
	# Global preferences

	- 설명은 간결하게
	- 일반적인 커밋 형식 사용
	- 변경사항 확인을 위한 터미널 명령 표시
	- 상속보단 합성을 선호
  이런식으로 작성하면됨
  
  settings.json는 모든프로젝트에서 기본적으로 설정되는걸 나열함
  보통 권한설정을 주로 하게됨
  또한 전역과 프로젝트가 병합되게됨(클로드md와 차이)
  
  keybindings.json은 cli에서의 핫키를 지정함
  
  projects/는 각 프로젝트별 에이전트 오토메모리를 관리함,사용자가 적을필요는없음(삭제할필요는 있을수있음..)
  이아래에 memory.md가 있고,memory.md가 너무 길어지면 주제별로 메모를 작성하는식으로 동작함
  
  rules/는 프로젝트의 rules/와 동일하지만 모든곳에 적용됨
  보통 개인코드스타일이나 커밋메시지양식같은걸 여기다가 적용해서 모든곳에서 사용하게함
  
  skills/는 프로젝트의 skills/와 동일하지만 모든곳에 적용됨
  
  commands/는 안씀
  
  output-styles/은 프로젝트의 skills/와 동일하지만 모든곳에 적용됨
  이건 보통 글로벌레벨로 사용하고,이건 각 마크다운 파일별로 출력스타일을 지정함
  이건 시스템 프롬프트에 지침을 추가하는 방식으로 동작함
  이걸 사용해서 클로드코드를 코딩 외 용도로 사용하거나,학습모드등을 추가하는식으로 사용할수있음
  보통 설정으로 특정 출력스타일을 지정할수있음
  예시로는
    ---
	description: Explains reasoning and asks you to implement small pieces
	keep-coding-instructions: true
	---

	After completing each task, add a brief "Why this approach" note
	explaining the key design decision.

	When a change is under 10 lines, ask the user to implement it
	themselves by leaving a TODO(human) marker instead of writing it.
  이런식으로 작성됨
  
  agents/는 프로젝트레벨과 동일한데,전역에서 사용할수있는 하위에이전트
  agent-memory/는 위의 전역레벨 에이전트들의 메모리임

  ~/.claude/plugins는 플러그인 저장위치

5.컨텍스트 윈도우	
  세션을 시작하면 기본적으로
	시스템프롬프트 4k 
	오토메모리 700
	Environment info 300:현재 디렉토리,os,깃저장소인지 등의 환경값들
	mcp tool (가변):mcp 설명
	Skill descriptions(가변):사용 가능한 스킬들에 대한 설명묶음	
	~/.claude/CLAUDE.md (가변,320정도):전역레벨 클로드.md파일
	Project CLAUDE.md (가변,2k정도):프로젝트레벨 클로드.md파일
  이 기본적으로 컨텍스트에 들어감
  즉 대략 10k정도는 기본적으로 컨텍스트에 들어간상태로 시작한다고 볼수있음
  
  여기서 프롬프트를 날리면 내 프롬프트가 컨텍스트에 추가되고,현재 디렉토리에서 파일들을 조회하면서 컨텍스트에 추가함
  이때 파일조회가 컨텍스트 사용량의 대부분을 차지하게되고,그래서 프롬프트에 구체적인 내용을 명시하는게 좋음
  또한 현재 조회하는 파일이 Rules에 포함되는 파일이라면,해당하는 룰도 컨텍스트에 추가함
  이때 터미널에 Loaded .claude/rules/룰이름.md가 표시됨
  그리고 클로드가 결론을 내린게 컨텍스트에 추가되고,그이후 작업이 컨텍스트에 추가됨(주로 edit)
  중간중간 훅이 있었다면,해당 트리거를 땡겼을때 훅도 실행될거고
  
  만약 서브에이전트를 사용한다면,매우 작은크기의 하위에이전트 생성 컨텍스트가 메인에이전트 컨텍스트에 추가되고,
  서브에이전트에서도 시스템프롬프트나 클로드.md등 기본적인 init세팅을 하고 알아서 작업함
  이후 서브에이전트가 작업을 완료하면 매우 작은크기의 최종 텍스트 응답과 토큰수,지속시간등의 메타데이터가 메인에이전트 컨텍스트에 추가되고,
  메인에이전트는 이걸 사용해서 효과적으로 컨텍스트를 압축해서 작업을 진행할수있음
  
  
  !git status같은 !가 붙은 셸 실행 명령은 컨텍스트에 추가되긴하는데,매우 작은크기의 영역만 차지함
  클로드가 직접 실행시키는게 아닌,결과값만 받아가기때문
	
  /스킬명 을 사용하면 스킬을 호출하는데,이시점에서 스킬의 상세내용이 컨텍스트에 올라감  
  /commit-push를 사용하면 해당하는 스킬의 본문이 컨텍스트에 올라가는식
  
  컴팩트를 하게되면 init에 들어갔던 기본컨텍스트와,현재까지의 모든 대화내용을 하나의 요약텍스트로 만들어서 컨텍스트에 추가함
  이 요약에는 요청 및 의도,주요기술개념 검토,수정된파일과 중요코드조각,오류 및 수정방법,보류중인 작업,현재 작업내용이 포함됨
  이건 기존 대화내용을 그대로 대체하며,도구출력내용과 중간추론과정은 삭제됨
  또한 rules/로 읽은내용도 다시 읽기전까진 추가되지않음
	
6.지침 및 메모리 저장	
  기본적으로 클로드코드에는 세션간에 공유되는 기록을 위한 두가지 메모리시스템이 있음
  클로드md와 오토메모리가 그거임
  클로드md는 사용자가 지침이나 규칙등을 기록하는거고,오토메모리는 빌드명령이나 인사이트등을 클로드가 직접 기록하는거임
  
*1.Claude.md
  클로드md에 내용을 추가할때는
    클로드가 같은 실수를 두번째로 할때
	코드리뷰에서 클로드가 이 코드베이스에 알아야할걸 발견했을때
	지난세션에 입력한것과 같은 수정 또는 설명을 채팅에 입력했을때
	새 팀원이 생산성을 높이기위해 같은 컨텍스트가 필요할때
  즉 같은작업을 두번이상 할때,이걸 클로드md에 추가하기 좋음
  
  클로드md는 위치에 따라 각각 다른 범위를 가짐
  크게
    글로벌레벨:회사 룰등
	프로젝트레벨:프로젝트 아키텍처,코딩표준등
	사용자레벨:코드스타일선호,개인 툴 단축키등
	로컬(claude.local.md)레벨:샌드박스url,선호하는 테스트데이터등
  을 넣기 좋음

  1.프로젝트 CLAUDE.md 설정
	프로젝트레벨 클로드md는 항상 컨텍스트에 로드됨
	그래서 200줄 이하를 목표로 하고,넘으면 룰을 사용하는게 좋음
	또한 마크다운으로 규칙을 그룹화 하는게 좋고,검증할수있을정도로 구체적인 지침이 좋음
		'코드를 제대로 적습니다' 보단 '2칸 들여쓰기 사용'
		'변경사항을 테스트합니다' 보단 '커밋하기전에 npm test' 실행
	이렇게
	만약 두 규칙이 서로 모순된다면,클로드가 알아서 선택함
  
  2.추가파일 가져오기
    @path/to/import를 사용해서 추가파일을 가져올수있음
	상대경로,절대경로 둘다 가능하고,재귀도 가능
	  @package.json
	  @docs/git-instructions.md
	이런식으로 가져올수있음
	
	또한 기본적으로는 클로드코드는 Agents.md를 읽지않는데
	  @AGENTS.md
	를 클로드md에 걸어두는식으로 같은걸 읽게할수있음
  
  3.CLAUDE.md 파일이 로드되는 방식
    클로드코드는 현재 작업 디렉토리에서 루트를 향해 올라가며 클로드md파일을 읽고 각 디렉토리를 확인함
	발견된 모든 파일은 각각 별개로 컨텍스트에 로드됨
	즉 현재 작업하는 디렉토리의 하위 클로드md는 신경쓰지않고,자신부터 루트까지만 읽는다는것
	또한 클로드md에서 <!-- maintainer notes -->를 사용하면,여기내용은 무시돼서 컨텍스트에 들어가지않음
	
	추가적으로 --add-dir을 사용해서 클로드에 현재 작업 디렉토리 외부의 추가디렉토리 엑세스권한을 줄수있는데,이때 거기의 클로드md파일은 로드되지않음

*2. .claude/rules/로 규칙 구성
  룰을 사용하면 규칙을 모듈식으로 만들수있고,컨텍스트공간을 절약하면서 노이즈를 줄일수있음
  단,항상 컨텍스트에 있을 필요가 없는 지침은 스킬을 사용할수있음
  
  룰은 .claude/rules/에 각각 하나의 md파일로 둘수있고(하위디렉토리도 허용됨),여기의 path포맷터로 특정 작업위치를 지정할수있음
  path포맷터가 없다면 claude.md와 동일하게 시작시 로드됨
  
  룰은 yaml포맷터로 작성됨
	---
	paths:
	  - "src/api/**/*.ts"
	---

	# API 개발 규칙

	- 모든 API 엔드포인트는 입력 검증을 포함해야 합니다
	- 표준 오류 응답 형식을 사용합니다
	- OpenAPI 문서 주석을 포함합니다    
  이런식임
  패스를 여러개두는것도 가능
	---
	paths:
	  - "src/**/*.{ts,tsx}"
	  - "lib/**/*.ts"
	  - "tests/**/*.test.ts"
	---

  또한 심볼릭 링크도 허용돼서,여러프로젝트를 묶어서 룰 하나를 사용할수도있음
  
  또한 사용자레벨 rule은 프로젝트 rule 이전에 로드되어서 더 높은 우선순위를 제공함
  
  만약 모노레포에서 상위 클로드md파일에 작업과 관련이 없는 지침이 포함된다면,
  claudeMdExcludes 설정을 통해 경로 또는 glob패턴으로 특정 파일을 건너뛸수있음
	{
	  "claudeMdExcludes": [
		"**/monorepo/CLAUDE.md",
		"/home/user/monorepo/other-team/.claude/rules/**"
	  ]
	}

7.권한 모드	
  권한모드는 쉬프트탭으로 갈수있는 모드들을 말함
  모드와 관계없이 보호된 경로에 대한 쓰기는 절대 자동승인되지않음
  모드에는
    default:기본설정,읽기 allow 나머지는 물어보고 진행,기본값
	acceptEdits:읽기,파일편집,일반적인 파일시스템명령(mkdir,mv,cp등),검토중인 코드 반복에 사용
	plan:읽기만 허용,변경전에 코드베이스 탐색후 플랜짤때 사용
	auto:백그라운드 안전검사를 포함한 모든작업에 사용,장시간 작업에 주로 사용됨
	dontAsk:사전승인된 도구는 자동허용,나머지는 거부,파이프라인에 쓰기좋음,완전한 비대화형
	bypassPermissions:모든작업 허용(yolo),격리된 컨테이너같은데서 쓰기좋음
  가 있음
  기본적으로 쉬프트탭으로 디폴트,액셉트에디트,플랜을 순환할수있고,나머지는 시작할떄 키면 추가됨
  
  acceptEdits는 클로드가 프롬프트없이 디렉토리의 파일을 생성하고 편집할수있음  
  plan모드는 클로드에게 변경사항을 연구하고 제안하게 지시하고,변경은 막음
  auto모드는 클로드가 권한프롬프트 없이 실행되게하는데,별도의 모델이 실행전에 잡업을 검토해서 이상하다싶은건 막아주긴함
  dontAsk모드는 사전승인된 도구만 허용하고,나머지는 전부 거부함
  bypassPermissions모드는 보호된경로를 제외한 모든걸 허용함(yolo모드임),보통 컨테이너같은데서 쓰면됨,아니라면 뭔일날진모름
	
  보호된경로는 기본적으로
	.git
	.vscode
	.idea
	.husky
	.claude(단 커맨드,에이전트,스킬,워크트리 제외,여기서는 직접 작업해서 추가해야하니까)
  가 있고,보호된 파일로는
	.gitconfig, .gitmodules
	.bashrc, .bash_profile, .zshrc, .zprofile, .profile
	.ripgreprc
	.mcp.json, .claude.json	
  가 있음
  대중 git관련과 ide관련을 다 막고,프로파일같은 관계없는 설정도 막는다고보면됨

*7.워크트리
  git worktree를 사용하면 병렬 클로드 세션을 쓸수있음
  즉 여러작업을 수행할때 각각의 세션이 충돌하지않게하는 방법임
  이건 --worktree플래그로 클로드코드를 켜서 실행하면됨,
	claude --worktree 분기이름
	claude --worktree 인증수정
	claude --worktree 인가수정
  만약 이름을 생략하면 랜덤한 이름을 붙임
  워크트리는
    <repo>/.claude/worktrees/<name>
  에 각각의 분기가 생성됨
  
  서브에이전트도 워크트리 격리를 사용해서 충돌없이 병렬로 작업할수있음
  워크트리 쓰라고 요청해도되고,아예 서브에이전트 설정에서 isolation:worktree로 설정해둬도됨
  
  워크트리세션을 종료할때
    만약 변경이 없었다면:해당 분기가 제거됨
	변경또는 커밋이 존재했다면:클로드가 워크트리를 유지할지 물어보고,유지한다면 다시 거기로 붙을수있음
  또한 고아가 된 워크트리는 cleanupPeriodDays 기간보다 길어지면 제거되는데,커밋되지않은 변경사항이 있다면 제거되지않고,
  --worktree로 만든 워크트리는 절대 제거되지않음
  
  워크트리는 새로운 체크아웃이라서 .env나 .gitignore을 포함하고있지않음
  그래서 만약 자동으로 이런걸 복사하게하려면 .worktreeinclude로 추가해두면됨
  이안의 패턴과 일치하면서 gitignored인 파일만 복사함
  
  또한 기본적으론 git을 기반으로 동작하지만,svn등을 사용해서 할수도있긴한데 안되는것도 있음

*1.클로드에게 작업을 검증할 방법 제공하기

  예를들면
    검증 기준 제공
        "이메일 주소를 검증하는 함수를 구현하세요"
	  대신
	    "validateEmail 함수를 작성하세요. 
	  예제 테스트 케이스: user@example.com은 true, invalid는 false, user@.com은 false입니다. 
	  구현 후 테스트를 실행하세요"
	ui변경사항을 시각적으로 검증
	    대시보드를 더 좋게 보이게 하세요
	  대신
	    [스크린샷 붙여넣기] 이 디자인을 구현하세요. 결과의 스크린샷을 찍고 원본과 비교하세요. 차이점을 나열하고 수정하세요
	증상이 아닌 근본 원인 해결
	    빌드가 실패하고 있습니다
	  대신
	    빌드가 이 오류로 실패합니다: [오류 붙여넣기]. 수정하고 빌드가 성공하는지 확인하세요. 근본 원인을 해결하고 오류를 억제하지 마세요
  이렇게 하라는것

*6.세션 관리하기
  대화는 되돌릴수있고,이걸 활용하면 좋음
  1.조기에 자주 방향 수정하기
    클로드는 첫시도에서 문제를 해결할수도 있지만,아니다싶으면 빠르게 수정하면 더 나은 결과를 낼수있음
	   esc:이상하다싶으면 인터럽트걸어서 멈출수있음,이때 컨텍스트는 보존되므로 방향을 바꿀수있음
	   esc+esc:이건 리와인드로 마지막 요청을 시작하기 전으로 돌이갈수있음,이때 컨텍스트와 코드상태가 같이 복원됨
	     꼭 마지막 요청이 아니라도 좀 더 멀리도 되돌아갈수있음
	   채팅으로 요청:Undo that 이런식으로 요청하면 변경사항만 되돌릴수있음(컨텍스트는 그대로)
	   /clear:그냥 컨텍스트를 초기화할수있음
	한 세션에서 같은문제에 대해 두번이상 방향을 수정했다면,컨텍스트 개판나있을테니까 초기화하고 더 구체적인 프롬프트로 다시 시작하는게 나음

  2.컨텍스트 적극적으로 관리하기
    압축은 최대한 터트리지않고,선제적으로 관리하는게 좋음
	  작업이 끝나면 현재 세션을 요약해서 기록한후에 클리어
	  클로드md에 세션요약기록의 위치를 적어두기
	  /btw로 컨텍스트에 들어가지않는 질문을 할수있음(빠른질문용)
	  
  3.서브에이전트를 사용하여 조사하기
	서브에이전트를 사용하면 컨텍스트를 거의 사용하지않고 작업을 진행할수있음
  
  4.체크포인트로 리와인드하기
    클로드는 변경전에 자동으로 체크포인트를 생성함
	esc2번이나 /rewind로 해당 체크포인트로 이동할수있음
	이때 대화만 복원하거나,코드만복원하거나,둘다 복원하거나 할수있음
