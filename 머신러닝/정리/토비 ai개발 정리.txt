*5.개발시작
  개발을 할땐 선택지가 여러개있음
    1.prompt->개발:간단한 작업일때
	2.prompt->plan->개발:일반적인 작업일때,이떄 플랜은 확인해보고가는게좋음
	  플랜은 클리어시 플랜이 사라진다는 단점이있음
	3.prompt->prd.md->리뷰->개발:좀 큰프로젝트일때 사용,prd안에는 기능에 대한 스펙,유저스토리,기술스택,아키텍처,데이터구조등이 들어감
	4.prompt->spec(기능에대한 스펙)->구현플랜(어떤 단계에 따라서 만들건지)->태스크리스트->개발:sdd방식의 접근방식
	5.prompt->슬라이스 레이어별로 개발:특정 엔티티의 레이어별로 개발,검증,가이드갱신
  이 작업이 어느정도 크기인지에 따라 다르게 선택해야함
  
  예를들면 기능에 대한 이야기를 다 한다음에,일단 엔티티만 먼저 만들어줘 한후에 엔티티들을 리뷰한후에 나만에 개발방식들을 요구하는식으로 접근할수도있고
  그냥 api부터 도메인까지 슬라이스별로 접근하면서 ai가 디폴트로 하는 방식을 내가 원하는 스타일로 좀 변경하는 방식도 있음
  이건 api부터 도메인까지 거기에 필요한것들을 가로축이 아닌 세로축으로 만드는느낌,
  보통 맨 처음에 ai에게 자기만의 구조 스타일을 제시해주기위해 사용(보통 이미 있으면 그거따라하니까)
  
  기본적으로는 아예 prompt->개발을 하거나,아니면 플랜문서를 만들어둔후에 어떤식으로 접근할지 생각해보는게좋음
  즉 3번이나 4번을 사용하는게 디폴트라고 보면됨
  3번과 4번의 차이점은,prd는 스팩과 구현플랜이 같이 섞여들어있고,그걸 따로 나눌거냐 아니냐의 차이임
  나누는게 좀 더 깔끔하긴한듯

*1.에이전트 동작 원리
  가장 잘 나와있는건 클로드코드의 작동방식 공식문서임
  
  ai가 에이전트처럼 동작하게 해주는걸 하네스라고 부름
  이게 코덱스나 클로드코드같은거임
  이건 ai를 둘러싼 도구들로,이걸통해서 ai를 통해 개발,각종 작업등을 처리할수있게됨
  
  우리가 프롬프트로 작업을 지시하면,에이전트 루프가 돌아감
  이건
    컨텍스트를 모으고
	액션을 하고
	결과를 검증하고,결과가 완료가 아니면 다시 이걸 컨텍스트로 사용
  이걸 검증이 ai가 만족스러울때까지 루프하는거임
  여기서 가장 중요한 구성요소는,추론용 모델과 툴로 구성됨
  툴은 이런 도구의 사용법을 ai한테 준다음에 이걸 사용하면 결과물을 받을수있게 하는것
  이걸 클로드코드가 대신 처리해줌
  즉 클로드는 모델이고,클로드코드는 툴+작업방식이라고 봐도됨
  
  만약 현재 프로젝트를 분석해줘 이런 프롬프트를 날리면,
  클로드코드는 내가 가지고있는 도구가 뭐가 있어라는걸 보내고,그중에서 클로드는 툴콜링을 해서 쓰는거임
  그러면 클로드가 bash를 쓰겠다고 하고 함수콜처럼 응답을주면 클로드코드는 bash로 폴더상태를 분석하고 결과값을 다시 응답에 담아서 요청을 다시날리는거
  이렇게 요청-응답을 반복하다가 더이상 툴콜링할게 없고,작업할게 없다면 루프를 끝내는거
  

  프롬프트를 날리고 ●Bash 이런거 하나하나가 다 툴임

*2.확장포인트 개요 및 플러그인 주의사항
  플러그인,스킬등 이런것들은 클로드코드에서 확장할수있게 확장포인트를 열어준거
  
  가장 실수하기좋은건 스킬이나 플러그인들을 막 추가하면 안됨
  이러면 컨텍스트가 엄청나게 더러워지고 성능도 엄청떨어지고 효율도 낮아짐
  
  제일 먼저 해야할건 클로드코드가 기본적으로 가지고있는 기본도구,에이전트가 뭐가있는지 알고 어떨때 이것들을 사용하면 될지를 알아야함
  그 다음으로는 오피셜 플러그인을 알면됨
  이것들은 기본으로 깔려있진않지만 안전하고 유용하다는거 검증된 플러그인들임
  이것들도 다깔진말고,꼭 필요한거만 까는게 좋음

  기본도구는 그냥 클로드한테 물어보면됨,뭐가있는지 어떻게쓰는지등
  플러그인이나 스킬을 추가하고나서도 물어보면됨
    네가 가지고 있는 도구가 어떤건지 알려줘.에이전트도 알려줘.

*6.서브에이전트 및 코드품질평가 에이전트 생성
  서브에이전트는 각각마다 세션을 가지고,작업을 수행한후 요약된 결과만 메인에이전트로 보내는 방식임
  
  에이전트로 만들기 가장 좋은건,코드품질을 평가하는 에이전트가 일단 가장 먼저 만들기좋음  
  이런작업들은 중간의 작업내용이 남아있을 필요가 없기때문에,이런것들을 에이전트로 만들기 좋음
  즉,중간의 진행사항이 필요없는 작업들의 경우,결과만 필요할경우를 뽑아내서 서브에이전트로 만드는것
  
  에이전트도 스킬이랑 비슷함,단 별도의 세션에서 동작시키는것
  코드품질평가를 스킬로 만들어도되는데,에이전트로 만들면 컨텍스트관리가 쉬워진다는거임
  
  에이전트를 만들땐,기본적으로는
    /agents
  로 하면됨
  이러면 프로젝트레벨로 할지,퍼스널레벨로 할지가 나오고,
  클로드로 만들지 직접 만들지가 나옴,여기서 클로드로 만들면되고
  그다음에 무슨 에이전트가 필요한지를 적어주면됨
    코드를 분석해서 코드품질을 평가하고 리포트를 생성해
	가독성,아키텍쳐,테스트,보안 등등 여러 품질 분야로 분석을 하고
	각각 점수를 내주고,점수를 다시 A-F등급으로 바꿔서 보여줘
  이런식으로
  이렇게 만들고나서는,해당 에이전트가 할일을 요청해서,제대로 실행되는지까지 확인해야함
    코드 품질을 평가해줘
  이런식으로 테스트를 해봐야함
  에이전트도 똑같이 툴목록에 들어가는방식이고,거기서 제대로 받아갈수있는지를 확인하는거
  기본적으로 디스크립션이나 이런데에 들어가는 단어를 비교하기때문에,잘 실행이 안되면 실제 만들어진 파일을 직접 좀 수정해야할수도있음
  
  서브에이전트는 기본적으로 백그라운드에서 병렬로 실행되고

*7.에이전트팀-TDD팀
  tdd는 
    레드(실패하는테스트) 
    그린(테스트를 성공시키는 코드) 
    리팩터(테스트를 성공시키는 코드를 리팩터링)
  로,이걸 내가 원하는 결과가 나올때까지 반복하는거임
  이걸 각각 에이전트로 만드는것
  그래서 각 에이전트들에게 작업을 시켜서 진행을 하는거임
  이때 에이전트팀으로 만들면 더 잘 만들수있음
  
  기본적인 서브에이전트는 메인과만 통신하지만,에이전트 팀을 사용하면 만들어진 에이전트끼리도 서로 커뮤니케이션할수있음
  에이전트팀은 기본기능이 아니라서 환경변수세팅을 해줘야함
  이것도 클로드코드한테 해달라고 하면됨
    ~/.claude/settings.json에 env로 agent team을 사용할수있게 설정해줘
  이렇게
  이러면 저 파일에
	  "env": {
		"CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
	  }    
  를 추가하는데,여기서 이상하게 할수도 있으니 잘 확인해야함
  
  이후에 에이전트팀을 만들면 되는데
    CreateTeam을 이용해서 Tdd를 수행하는 agent team을 구성해줘
	-Red:실패하는 테스트 작성.테스트를 실행해서 실패하는지 확인해
	-Green:실패하는 테스트를 성공시키기위한 코드만 작성해줘
	-Refactor:작성된 코드를 리팩터링해줘
	기본적으로 red-green-refactor-red-green-refactor이런식으로 반복돼
	Team lead는 주어진 개발 요구사항을 받아서 task를 분할해서 작성하고 팀과함께 Tdd를 진행시켜줘
  이렇게 만들면됨,이렇게 만들어두고 잘되면,이렇게 에이전트 팀 만드는걸 스킬로 만들어도됨
  이때 얘가 클로드코드가 가지고있는 에이전트 팀 만드는 기능을 쓰지않고,지맘대로 직접 구현하려고 하는경우가 있음(보통 위에서 환경변수이름을 이상한거로했을때)
  이러면 일단 인터럽트를 걸고 확인해보면됨
  
  제대로 팀을 만들면 팀웍스를 이용해서 화면분할을 하고,각각 그 에이전트하나마다 창을 하나씩 할당을 함
  기본적으로는 팀리드(메인)에서 요청을 날리고,각각의 에이전트가 필요한일이 있다면 거기다가 요청을 날려도됨
  이러면 red green refactor red green refactor 이런식으로 리드가 태스크를 만들고 그걸 하위에이전트가 실행하는식

  그래서 클로드를 초기화하는 기준이 되는게 보통 새 모델이 출시됐을때임
  물론 이때도 내가 도구가 필요했던 작업들을 가진 레퍼런스 프로젝트를 하나 가지고 있으면 좋음
  그걸해보면서 아 이정도는 말 안해도 해주네 같은건 도구목록에서 빼버리는거
  
  그리고 다른 에이전트(클로드,코덱스,제미나이등)과 협업하게 하는것도 있음

  그래서 코덱스한테 코드리뷰를 시키고,클로드코드한테 이렇다는데 어떻게 생각해?하고 서로 토론을 붙여놓고,맘에드는거만 수정을 시키는거
  이런식으로 테스트를 잘 작성해서,핵심기능은 ai가 코드를 망쳐놔도 테스트로 검증이 가능하게 세팅해두면 좋음
  
  ai가 더 일을 잘할수있는 환경을 꾸며주고,그거를 개선하는 연습을 해야함
  그리고 플러그인이나 이런건 리뷰를 한번 시키고,보안과 관련된 문제가 없는지 검토해달라고 하는식으로 하고,
  내가 원하는 방식으로 바꿔서 써도됨 어짜피 오픈소스니까

*4.스킬
  스킬은 우리가 어떤 워크플로우중에 필요한 작업들,좀 긴프롬프트로 써야했던걸 간단하게 만들어주는게 가장 많이쓰이는 목적이고,
  레퍼런스 용도로도 잘 사용됨
  이건 ai가 알고있지않은것들이나,회사만의 코딩관례나 우리팀이 중요하게 보는것들,현재 집중하고있는부분등을 매번 설명해주기 힘드니까
  이걸 클로드md에 넣어도 되지만,이게 기술에 특화된부분이다(세부사항)싶으면 스킬로 떼어내기좋음
  이럴땐
    1.ai와 필요로 하는걸 계속 대화 or 웹사이트를 가지고 이걸 공부해라고 시키기
	2.그걸가지고 나랑 대화했던 내용을 가지고 스킬로 만들어줘(지금까지 cmux로 했던걸 스킬로 만들어줘)
  이런식으로 할수있음
  이러면 정보를 잘 추리고,필요한 코드나 이런게 있다 이런거까지 모아서 스킬을 만들어줌
  그러면 이후로는 그냥 스킬을 호출하면됨

  그래서 내가 쓴 기술,내가 자주쓰는 개발방법 이런것들을 스킬형태로 잘 만들어두면 내가하는거랑 비슷하게 하기 좋음
  보통 유명한 스킬들은 범용적임
  스프링이든,타입스크립트등 누구나 쓸수있게 보통 만들어두는데,이런걸 가져다쓰는것도 물론 필요하지만,

*7.핵심 워크플로우
  핵심은 탐색->계획->구현->커밋(검증)임
    탐색:플랜모드에 진입해서,
	  "이 프로젝트를 니가 한번 분석해봐" 
	  혹은
	  "나는 xx부분작업을 학거야,네가 지금 만들어둔 설계문서,도메인코드,api코드를 먼저 한번 살펴봐" 
	  라고 시켜서 현재 프로젝트에 대한 컨텍스트를 명시적으로 추가
	계획:플랜모드로 어떤식으로 작업할지에 대해 계획을 짜게 하는것
	  즉 클로드가 어떤순서로 작업할지에 대한 계획을 짠다음,내가 그걸 보고 이렇게해도될지를 판단하는것
	  이때 클로드가 만들어준 문서를 잘 보고,여기엔 내용을 추가해야겠다,이건 지금 필요없을거같다를 클로드랑 대화를 되게 많이 하면서 만들어나가야함
	구현:실제로 코드를 구현하는것
	커밋(검증):이런 사이클로 구현했을때,구현을 마치면 커밋을 해서 다음 작업이 잘못돼도 돌아올수있는 체크포인트를 만들라는거
  즉 중요한건 계획에 시간을 많이쓰는것,그래야 구현이 잘됨
  tdd는 이 안에서 구현에서 사용하는 세부워크플로우임
  그리고 바로 계획을 하기보다는,탐색을 시키고 계획으로 시키는게 좋음,이걸 브레인스토밍이라고도 부름

*8.브레인스토밍과 리서치
  맨땅에서 하는 브레인스토밍레벨이라면(만들어둔게없다면),리서치를 먼저 시키는게 좋음
  즉 탐색을 리서치로 대신하는것
  만약 블로그를 만든다면,
    요즘에 유명한 블로그서비스들을 보고 기능을 분석하고 인기있는 서비스들을 찾아서 분석하고 특징,장단점같은걸 분석해봐 
  이런식으로 시킨후
    난 xx부분을 포커스를 두고 개발을 싶은데 니가 그런거에 대한 아이디어를 좀 정립해줘
  이렇식으로 시키는것
  이러면 기초적인 리서치가 끝나고,이걸가지고 
    이걸 이제 개발할거야,이거에 대한 스펙을 만들어줘
	스펙에대한 플랜을 세워줘
  이런식으로 플랜단계로 들어가는것
  
  이때 중요한건,한번에 너무 많은걸 만들지않고,최소한의 기능만 가지고 만드는게 좋음
  보통 플랜에는 넣어두지만,최소한의 기능이 다 만들어 진 다음에 확장하는게좋음
  
  이 탐색->계획->구현->커밋은 초반에 mvp를 빨리 뽑아낼떄도 유용하지만,
  아주 세세한 기능을 하나 추가하거나,기능을 조금 변경하거나,디버깅을 할떄도 이런식으로 하는게 좋음
  
  그냥 버그났어 고쳐줘 이거보단
    이런 에러가 났는데 이게 무슨 문제야?
	이걸 고치려면 어떤식으로 작업을 할까?
	그걸 확인하는 테스트는 어떻게 만들까?
	그렇게 작업해줘
  이런식으로 가볍게라도 탐색->계획->구현->커밋을 밟아가는게좋음

    /brainstirming xxx서비스 개발하고싶어,어쩌고저쩌고 상세내용,기술스펙(스프링부트,mysql등)
  이러면 얘가 체크리스트 테스크를 만들고 진행함
  보통
    프로젝트 컨텍스트 탐색//현재 폴더를 탐색해서 진행사항등을 확인하고,앞의 세션대화내용을 다시 확인(리서치 시킨거등)
	비쥬얼 컴페니언 제안//아키텍처등을 브라우저로 확인할수있게 해주는거

	2~3개의 접근법 제안

	  보통 데이터모델 설계도 여기에 같이 들어감

	스펙 셀프리뷰
	사용자 스펙 리뷰

	  여기서 내가 생각하는거랑 좀 다르다 그러면 초반에 이걸 꼼꼼하게 잡으면 좋음
	  예를들어 컨트롤러만들때 어떤식으로 메서드나 어노테이션을 쓰는지 이런것들을 내가 원하는 방식과 다르면 지정을 계속하는거
	  그리고 이런걸 클로드md에 집어넣어두라고 하면됨,이러면 이후에 브레인스토밍을 할때도 그걸 반영해서하니까
	  이런걸 초반에 잡아둬야 프로젝트 전체에 통일성이생김
  이런순서로 진행할거임
  그리고 보통 처음엔 기본기능을 충실하게 mvp를 만든다음에,이걸 검증하고 그다음에 기능을 올리고 이런식으로 올라가는게 좋음
  그리고 코드를 구현하는걸 ai한테 맡겨야지,설계는 꼼꼼하게 확인하고 선을 지키는지 계속 확인해야함
  보통 브레인스토밍은 30분이 기본이고,계속 수정하면 한시간정도는 사용됨
  
  그리고 스펙을 받은다음(사용자 스펙 리뷰때),제미나이나 코덱스한테도 리뷰를 해달라고 하는것도 괜찮음
  그 이후에 구현계획을 만드는것
  이때 가장 무식한방법은 직접 날려보는거고,더 나은 방법은 플러그인이나 스킬을 사용해서 그걸로 요청을 할수있게  스킬을 만든다음,
  그걸사용해서 리뷰를 받아보라고 하는것
  이건 처음부터 요청해도되고,사용자스펙리뷰때 인터럽트를 걸고 해달라고 해도됨
  이런식으로 여러 ai한테 맡길땐,내용을 읽어보고 직접 판단할수도있고,제미나이코덱스클로드 3개가 다 의견이 같은거만 진행해 이런식으로 할수도있음
  
  그리고 중요하지만 지금단계에서는 굳이 필요없다 그러면 깃헙이슈로 올리라고하면됨

  그리고나서 구현계획을 리뷰를 해보고,만약 스텝이 크다면(할게 많다면),이 단계에서 볼걸 충분히 생각해보고 어느정도 정리가 되면 커밋을 하는게 좋음
  그리고 여기서 발견한 문제나 이런걸 이스탭이 아닌 다음단계에서 다시 브레인스토밍부터 시작해서 진행하는거
  예를들어 ui가 맘에 안들어 이러면 브레인스토밍으로 그걸 다시 실행하는거
  
  이렇게 구현계획이 만들어줬으면 알아서 실행을 할거임

*14.퍼미션과 훅 설정
  미리 퍼미션을 설정하려면

  보통
    bash(codex:*)
	bash(git add:*)
	bash(git commit:*)
	bash(git init:*)
	bash(xargs -0 ls -t)
  정도는 허용해두면 편함
  추가로 맨날 쓰는거중 안전한거는 해두면됨
  
  deny는 rm -rf같은 위험한것들을 원천적으로 차단하면됨
  또한 프롬프트인젝션에도 대비해야함
  
  보통 deny는 ai가 읽으면 안되는것들에 걸어두는게 좋음
  Read()나 Edit으로 절대 외부에 공개되면 안되는것들을 못읽게하는데 사용하는것
  퍼블릭키 프라이빗키나 aws키같은거
  
  가끔 한번씩 설정을 확인해보는게좋음
  그리고 확률적으로 퍼미션설정은 무시될수있음,그래서 사용되는게 훅임
  훅으로 어떤 명령이나 도구를 실행하기전에 뭘 끼워넣을수있는데,여기다가 블록 데인지러스 훅같은걸(토비플러그인) 달아두면 차단을함

*15.컨텍스트 초기화
  컨텍스트가 1M까지 올라왔지만,그래도 200k~300k쯤에서 끊고 클리어하면서,지금까지 했던 작업들에 대한 문서를 만드는게 좋음
  그냥 컴팩트를 막기위한 용도로 1M으로 올라왔다고 생각하는게 좋음

*16.ai시대의 코드리뷰 문화
  ai로 코딩을 했다면,코드리뷰를 할때 프롬프트도 같이주면 코드리뷰가 쉬워짐
  어떤 대화들을 주고받아서 이 코드가 나왔다 같은느낌으로

*17.ai코딩철학
  뭐 만들어줘 띡 하고 끝나는건 간단한레벨에서만 가능하고,비즈니스레벨로 사용하려면 코드레벨의 리뷰도 필요하고,
  내가 신뢰할수있을만한 코드가 나올수있게 ai를 트레이닝시키고,이걸 하네스로 바꿔야함
  
  모델이 업데이트되고 클코가 업데이트되면 기존 하네스/프레임워크가 쓸모없어져서 다시만들어야하는경우가 꽤있음
  그래서 버전업이 되고나서 그걸 다시 검증하는 작업이 필요함
  클로드코드팀은 어떻게 스킬을 만들어 쓰나요? 영상 참조
  
  대충 최신 스킬크리에이터는 스킬을 쓰는것과 안쓰는것중 뭐가 더 나은지를 체크해줌
  그래서 업데이트가 되면 이걸 사용해서 확인을 해봐야함

*18.마무리
  영상보는거나 그런거도 좋지만,가장 중요한건 시간을 많이써봐야함
  하네스는 둘째문제고 자기자신의 워크플로를 다루는능력을 늘려야함
  범위를 크게잡아야할때도있고,테스트 하나만 딱 만들고 넘어가야할때도 있고
  
  ai가 뭔가 내가 모르는걸 해주면 그걸 공부해야함
  
  또한 컨버세이션 세이브스킬을 사용해서,커밋직전에 훅을 걸어두고,지금까지 작업한 내용들을 요청과 작업내용을 기록하는것도 좋음
  이건 어떤 도구를 사용했고,무슨작업을 요청했고,무슨작업을 했고,뭘 변경했고를 기록해줌


4.4부
*1.랄프 플러그인
  랄프는 깃헙에서 받을수있고,크게 /prd,/ralph,/ralph-loop 를 사용하기위해 사용됨
  그중 /ralph-loop는 기본적으로 클로드에 포함되어있음
  
*2.ai코딩 워크플로우 4단계
  기본 워크플로우는
    탐색
	계획
	  플랜모드
	  슈퍼파워스
	  랄프 /prd,/ralph,/ralph-loop
	구현+검증
	커밋
  인데,여기서 랄프는 작업을 중간에 끝내지않고,시작조건을 완료할때까지 우직하게 반복함
  그냥쓰면 하다보면 중간에 멈춰버리는데,이걸 막아줌
	
*3.prd스킬-유저스토리와 완료조건
  랄프의 /prd는 요구사항,스펙을 만들어내는 작업인데,이걸쓰면 간략하고 쉽게 나한테 명확화 질문을 거쳐서 스펙을 뽑아줌
  이때 이걸 유저스토리라는 개념으로 잘 나눠서,어떤단계를 밟아서 진행을 하고,스토리를 완성할떈 이런이런부분을 다 검사해야해 이렇게 완료조건을 줌
  그다음에 이걸 json으로 만들고 랄프루프까지 연결할수있음

*4.진행중인 프로젝트 작업
  진행중이던 프로젝트에서 작업을 할땐,일단
    프로젝트를 꼼꼼하게 분석해줘
  이렇게 탐색을 시키면됨
  이러면 컨텍스트에 프로젝트내용을 올리게됨
  
  그뒤에 플랜을 짜면되는데,이때 작업이 크지않다면 랄프의 /prd를 사용하면 좀 더 짧게 끝나게됨
    /prd xxx기능을 만들어줘
  이런식으로 하면됨,그러면 다시 역질문들어오면서 구체화를 하게됨
  플랜을 짤땐
    완전히 명확하게 무슨 코드가 들어갈지 알고있다:클로드 기본 플랜
	이 둘의 사이 중간쯤이다:/prd
	완전히 새로운 피처를 추가한다,기능이 여러가지 고려할게 많거나 중요한 기술의 변화등 큰변화가 예상된다:브레인스토밍
  이런느낌으로 사용하게됨
  보통 로그인이 이미 있을때,로그아웃기능을 만들어줘 이런정도의 작업일때 prd를 사용하게됨
  
  prd를 만들면 한방에 만들어주는게 아닌,유저스토리(유저관점에서 이런기능이 되야해)를 만들고,거기서 나눠서 작업할수있게 단계를 나눠서 md를 만들어줌
  여기엔 사용자로써의 설명과,인수조건(완료조건)을 나열해줌
  이걸 읽어보고,수정을 하고 구현해달라고하면됨
  그리고 이때 랄프를 쓰면,이 유저스토리를 보고 구현이 오래걸릴거같다(10분정도이상)하는걸 더 쪼개주고,ai가 이해하기편한 json으로도 바꿔줌
  이건
    /ralph
  하면 해줌
  그리고 랄프루프로 작업을 시킬때,얘는 반복마다 새 컨텍스트로 시작함
  즉 한번돌고,완료됐는지를 확인하고,완료가 아니라면 다시 새 컨텍스트를 열어서 작업을 재개하는방식

*5.랄프루프 실행
  기본적으로 랄프루프는 쉘스크립트로 실행했는데,요즘은 그냥 클로드코드안에 포함되어있음
  근데 클로드코드안에있는 랄프루프는 새 컨텍스트를 여는게 아닌,컨텍스트가 유지됨
  둘다 장단점이 있음
  랄프루프는 완료조건을 충족할때까지 계속 새로운 시도를 시키기에 적합하게 만들어진 아이디어고
    테스트 커버리지가 70%일때,이걸 90%로 만들어줘 하면서 돌리기
  이건 플랜(유저스토리)를 만들고 이걸 완료될때까지 반복시키는게 이론상 되야하지만,보통 잘 그렇게 동작을 안하려고함(강제중단)
  
  
  어떤식으로 쓰든,랄프루프를 돌리기위한 프롬프트가 필요함
  이건 그냥 랄프 깃허브가서 prompt.md를 받아오면됨(복붙)
  그리고 최대 반복횟수와,특정조건을 만족하면 작업을 종료해줘라는 옵션을 넣을수있음
  보통
    /ralph-loop @prompt.md --completion-promise "COMPLETE"
  이런식으로 던짐(프롬프트 확인해보고 수정해서쓰면됨,기본적으론 prd.json을 읽고 작업)
  
  랄프루프의 단점이자 한계는 프롬프트가 매번 똑같다는것
  루프를 돌면서 새로운걸 발견하고,그래서 이런게 좀 별로더라 했을때도 프롬프트가 똑같다는것
  그래서 프롬프트를 계속 업그레이드해주는 스킬들도 있음(지금까지 발견한걸 토대로 프롬프트를 개선해줘 이런식)
  
  랄프 플러그인을 사용하면 이걸 쓸때 자동으로 브랜치를 따줌
  그리고 자기가 한 작업에 대해서 progress.txt에 기록을 남기고,그걸 다시 읽어가면서 작업함
  
  랄프루프는 완료조건을 기준으로 루프를 돌리기때문에 검증을 계속 하면서 작업함
  즉 구현/검증을 전부 처리할수있음
  주의할점은 랄프루프를 돌리면 유저스토리 하나를 완료하고 커밋을 해버림
  그래서 전체기능을 다 넣어서 커밋하고싶다고 하면 중간에 커밋하지말라고 명시해줘야함
  
*6.플랜vs슈퍼파워스vs랄프
  기본적으로
    플랜:간단한작업
	슈퍼파워스:큰작업 or 처음에 스펙만들때 사용
	랄프:슈퍼파워스보다 작고,플랜보다 큰작업,루프까지 돌릴수도있고 /prd로 끝낼수도있음(작업크기에 따라)
  이렇게 씀
  
  또한 클로드코드가 잘 모를만한 기술은 한번 학습을 시키고 스킬로 만드는걸 습관화하자
  
  정식 작업을 할떈 먼저 ui를 만들고,프론트라면 html로 뽑고,그다음에 그걸 문서로도 만들고 작업을 시작하는게 좋긴함
  
  실무를 할땐 작업하는 범위를 세밀하게 조정할 필요가 있음
  그래서 ui까지 먼저 띄우는거만 작업해두고,거기서 기능추가하고,로직같은거 tdd하고 이런식
  작업이 크지않다 싶으면 그냥 통으로 던져도되긴하지만
  
  llm코딩의 핵심은 전체 프로세스안에서 어떤게 필요하고,제품이 완료가 될때 어떤 기능 하나하나가 이렇게 상세하게 동작하는지에 대해서 떠올릴수있어야함
  기획쪽 일과 더 가까운데,이런일을 훈련해야함
  아니면 그냥 만들어두고,그걸 개선하는 방식을 써도되긴함
  
  내가 llm에게 어떤 용어를 썼을때,어떤식으로 요구사항이 갔을때 어떤 결과가 나오겠구나를 파악하는 연습이 필요함
